1. Objectif

Ce document concerne le MVP (itération 1). La Spécification Produit contient le périmètre complet.

Le MVP remplace le papier pour la planification de la semaine et les notes de cours d'un étudiant en Licence.

Hypothèse : un étudiant qui utilise le papier aujourd'hui utilisera l'app 3 jours ou plus par semaine, si l'app planifie le travail automatiquement et garde les notes avec chaque cours.

Le MVP doit montrer que :

  1. La saisie est plus rapide que le papier.
  2. Le planning de l'app est réaliste. L'étudiant le suit.
  3. Les étudiants rouvrent leurs notes de cours plus tard.
  4. Les notes et le planning sont connectés : les tâches écrites dans une note de cours vont dans le planning.

2. Bêta-testeurs

  • Deux étudiants en Licence au départ. Aujourd'hui, ils utilisent le papier et leur mémoire.
  • La bêta est gratuite. Chaque étudiant a un compte. Il n'y a pas de groupes.
  • Retours : métriques d'usage, et courts échanges avec les testeurs à intervalles réguliers.
  • Ajouter des testeurs quand les testeurs demandent à inviter des camarades.

4. Boucle principale

Le produit est une boucle. L'étudiant donne du travail. L'app le planifie. L'étudiant le fait. L'app replanifie ce qui n'est pas fait. Les notes et les examens alimentent la boucle.

5. Parcours utilisateur

Chaque parcours a un déclencheur, des étapes et un résultat. Les points ouverts sont des manques. La section 7 donne une proposition pour la plupart d'entre eux.

P1. Onboarding (première utilisation)

Déclencheur : l'étudiant ouvre l'app pour la première fois. Cible : un premier planning en moins de 5 minutes proposition.

  1. S'inscrire avec un email.
  2. Créer le semestre. L'app propose les dates du semestre en cours. L'étudiant indique la première semaine A.
  3. Ajouter les cours : un nom et une couleur pour chacun. Le nom court est optionnel.
  4. Saisir l'emploi du temps hebdomadaire. L'étudiant peut passer cette étape et la faire plus tard.
  5. Régler le temps libre : accepter la valeur par défaut en un tap, ou la modifier.
  6. Ajouter les premières tâches et les examens avec la saisie rapide.
  7. L'app affiche la vue Aujourd'hui avec le premier planning.

Résultat : l'étudiant a un planning dès le premier jour.

Points ouverts : les états vides (pas d'emploi du temps, pas de tâches) ; l'ordre des étapes 4 et 5 quand l'étape 4 est passée.

P2. Boucle quotidienne

Déclencheur : l'étudiant ouvre l'app.

  1. La vue Aujourd'hui affiche les séances, les blocs (avec leur raison), les échéances et les alertes.
  2. À un bloc : démarrer (optionnel), puis fait. L'app demande le temps passé (optionnel, un tap : « comme prévu », ou une valeur).
  3. Ou passer. Le travail retourne à la tâche. Le planificateur le replanifie.
  4. Les blocs passés sans action deviennent manqués à la prochaine ouverture de l'app. Le planificateur replanifie le travail.
  5. Quand le travail prévu d'une tâche est fait, l'app demande : « La tâche est-elle terminée ? » (Terminée / Besoin de plus de temps : +30 min, +1 h, +2 h).

Résultat : l'étudiant suit le planning. Les estimations s'améliorent.

Points ouverts : le message pour les blocs manqués (sans culpabiliser).

P3. Saisie rapide

Déclencheur : l'étudiant se souvient d'un travail. La saisie est disponible depuis chaque écran.

  1. Cliquer sur le bouton de saisie ou appuyer sur Cmd+K.
  2. Écrire une ligne : « DM compta vendredi ».
  3. L'app affiche des pastilles : cours Comptabilité générale, type DM, échéance vendredi. L'étudiant corrige une pastille en un tap.
  4. Valider avec Entrée. La tâche reçoit l'estimation par défaut de son type. Le planificateur la planifie.

Résultat : la tâche est dans le planning en quelques secondes.

Points ouverts : aucune date trouvée (règle C5) ; aucun cours trouvé (règle C4).

P4. En cours : notes et tâches

Déclencheur : une séance commence.

  1. Taper sur la séance (vue Aujourd'hui ou calendrier). La note de séance s'ouvre. Elle est liée à la séance et au cours.
  2. Écrire.
  3. L'enseignant donne un travail. L'étudiant écrit une ligne de tâche dans la note.
  4. L'app crée la tâche avec le cours de la note. Le planificateur la planifie. La ligne affiche le statut de la tâche.
  5. Un panneau latéral affiche les tâches ouvertes et le prochain examen du cours.

Résultat : les notes et le planning sont connectés.

Points ouverts : la syntaxe d'une ligne de tâche ; ce qui se passe quand l'étudiant supprime la ligne (règle N-R3).

P5. Ajouter un examen

Déclencheur : l'enseignant annonce un CC, un partiel ou un oral.

  1. Le saisir (« partiel compta 15/11 ») ou ouvrir le formulaire d'examen.
  2. Indiquer le type, la date et le coefficient (optionnel).
  3. L'app crée les tâches de révision avec les règles du type (règle E1).
  4. Le planificateur les planifie avant l'examen.

Résultat : la révision commence au bon moment, sans effort.

Points ouverts : les règles de révision ; la modification des tâches de révision générées (règle E3).

P6. Ajuster le planning

Déclencheur : le planning ne correspond pas à la vraie journée.

  1. Déplacer un bloc (glisser dans le calendrier, ou « déplacer » dans la vue Aujourd'hui). Le bloc devient épinglé.
  2. Le planificateur replanifie les autres blocs autour, en dehors de la fenêtre de stabilité.
  3. Si le travail ne tient pas avant une échéance, l'app affiche une alerte de surcharge avec des actions.

Résultat : l'étudiant contrôle le planning. L'app fait toujours la planification.

Points ouverts : désépingler un bloc (règle B4) ; l'alerte après « accepter le risque » (règle S9).

P7. Changement d'emploi du temps

Déclencheur : un cours est annulé ou déplacé, ou l'emploi du temps change.

  • Une séance : l'ouvrir, puis l'annuler ou la déplacer. Les autres semaines ne changent pas. Le planificateur utilise le nouveau créneau libre.
  • La règle : modifier le jour, l'heure ou la salle. Les séances futures changent. Les séances avec une exception ou une note ne changent pas. L'app affiche les conflits.

Résultat : l'emploi du temps reste juste, sans nouvelle saisie.

P8. Retrouver et réviser

Déclencheur : l'étudiant cherche une note ou prépare un examen.

  1. Ouvrir la recherche. Écrire des mots. Ouvrir un résultat (note, tâche ou cours).
  2. Ou ouvrir un cours : ses séances avec notes, ses tâches et son prochain examen.

Résultat : les notes sont réutilisées (critère de succès 4).

P9. Voir la semaine

Déclencheur : dimanche soir ou lundi matin.

  1. Ouvrir le calendrier de la semaine : séances, blocs, échéances, examens et alertes.
  2. Filtrer par cours si nécessaire.
  3. Ajuster le planning (P6).

Résultat : l'étudiant voit la charge avant le début de la semaine.

P10. Réglages et données

  • Temps libre : le modifier. Le planificateur replanifie.
  • Restaurer, exporter, supprimer le compte : hors du MVP en libre-service. Le testeur envoie une demande. Un fondateur le fait avec un script d'administration (voir section 7.7).

7. Règles métier

7.1 Planificateur

IDRègle
S1Les blocs vont seulement dans le temps libre, hors des séances, et avant l'échéance de la tâche.
S2Ordre : échéance la plus proche d'abord, puis priorité. S2 donne l'ordre de traitement des tâches. S12 donne l'endroit des blocs.
S3Durée d'un bloc : minimum 30 min, maximum 90 min proposition. Une tâche de plus de 90 min reçoit plusieurs blocs.
S4Maximum par jour selon les réglages du temps libre. Par défaut 3 h proposition.
S5Les blocs épinglés ne bougent jamais.
S6Fenêtre de stabilité : les blocs des prochaines 24 h ne bougent pas proposition. Exceptions : l'étudiant passe ou déplace un bloc, ou une séance dans la fenêtre change.
S7Hors de la fenêtre, un bloc reste à sa place s'il est encore valide. Cela limite les changements.
S8Déclencheurs : modification d'une tâche, d'un examen, d'une séance ou du temps libre ; un bloc passé ou déplacé ; l'ouverture de l'app (rattrapage, B3). Pas de tâche planifiée.
S9Surcharge : pour une échéance, le travail dû avant elle est plus grand que le temps libre avant elle. L'app affiche l'échéance et le temps manquant. Actions : réduire l'estimation, supprimer une tâche, ajouter du temps libre, accepter le risque. Après « accepter le risque », l'alerte revient seulement si le temps manquant augmente.
S10Chaque bloc a une raison : l'échéance et le travail restant.
S11Chaque replanification d'une tâche augmente replanCount. À 3, l'app prévient l'étudiant (P9).
S12Placement : pour chaque tâche (ordre S2), le planificateur met les blocs dans le premier temps libre valide, à partir de la date de début de la tâche (S15). La limite S13 étale le travail sur plusieurs jours. Résultat : le travail commence tôt, et un retard garde de la marge.
S13Limite par tâche et par jour : 1 bloc, donc 90 min au maximum proposition. Exception : si la limite empêche de finir avant l'échéance, le planificateur peut mettre un 2e bloc le même jour. Il fait cela seulement les derniers jours avant l'échéance.
S14Marge : le planificateur essaie de finir une tâche 1 jour avant son échéance proposition. Si le temps manque, il utilise le dernier jour. S9 (surcharge) utilise l'échéance réelle, pas la marge.
S15Date de début : une tâche peut avoir une date notBefore. Les blocs ne vont pas avant cette date. Les tâches de révision l'utilisent : la date de l'examen moins la fenêtre de la règle (E1).

7.2 Blocs de travail

IDRègle
B1États : planned (prévu), done (fait), skipped (passé), missed (manqué). Seuls les blocs planned peuvent changer.
B2Un bloc fait compte son temps passé. Si l'étudiant ne donne pas de valeur, il compte le temps prévu.
B3Rattrapage à l'ouverture de l'app (au plus une fois par heure) : les blocs planned terminés dans le passé deviennent missed, puis le planificateur replanifie. Le message est neutre : « 3 blocs ont été déplacés plus tard ».
B4Un bloc déplacé est épinglé. L'étudiant peut le désépingler (P6).
B5Un bloc dans le passé ne peut pas être déplacé.

7.3 Tâches et examens

IDRègle
K-R1États : todo (à faire), in_progress (premier bloc fait), done (terminée).
K-R2Travail restant = estimation − temps des blocs faits.
K-R3Travail restant ≤ 0 et tâche non terminée : l'app demande « Terminée ? » ou « Besoin de plus de temps ? » (K5).
K-R4Tâche terminée : les blocs prévus dans le futur sont supprimés.
K-R5Estimations par défaut proposition : DM 120 min, lecture 45 min, compte rendu de TP 180 min, exposé 180 min, révision 60 min. Ces valeurs sont des données (table TaskType), pas du code.
K-R6Une tâche sans échéance n'est pas planifiée. Elle est dans la liste « Sans date » (K8).
K-R7Une échéance sans heure signifie la fin de ce jour, 23:59 heure locale.
E1Règles de révision proposition : CC = 2 × 60 min dans les 5 jours avant ; partiel = 5 × 60 min dans les 14 jours avant ; oral = 2 × 60 min + 1 × 30 min de répétition dans les 7 jours avant. Ces règles sont des données (table RevisionRule). Chaque tâche de révision a une échéance (la veille de l'examen) et une date de début (S15).
E2La date de l'examen change : les tâches de révision se déplacent avec elle.
E3Une tâche de révision modifiée par l'étudiant n'est plus générée à nouveau.

7.4 Analyseur de saisie rapide

IDRègle
C1Normaliser : minuscules, sans accents. La casse et les accents ne changent pas le résultat.
C2Dates : aujourd'hui, demain, après-demain, noms de jours (le prochain), « le 12 », « 12/10 », « 12/10/2026 », « semaine prochaine », « dans 3 jours ». Heure optionnelle : « 14h », « 14h30 ».
C3Types : dm → devoir ; tp, compte rendu → compte rendu de TP ; exposé, oral, présentation → exposé ; lire, lecture → lecture ; réviser → révision ; cc, partiel, exam → examen.
C4Cours : alias ou nom court exact, puis début du nom, puis texte proche. Sous un seuil : pas de cours. Un mauvais cours est pire que pas de cours.
C5Pas de date trouvée : la tâche est enregistrée dans « Sans date ». La pastille affiche « Sans date », et un tap ouvre un sélecteur de date.
C6Les mots qui ne sont ni une date, ni un type, ni un cours forment le titre.
C7L'analyseur est une fonction pure. Chaque erreur d'analyse de la bêta devient un cas de test.

7.5 Emploi du temps

IDRègle
T-R1Une règle stocke l'heure locale et un fuseau horaire. Un cours à 10:00 reste à 10:00 après le passage à l'heure d'hiver.
T-R2L'app crée une ligne de séance pour chaque date du semestre, quand la règle est enregistrée.
T-R3Modification d'une règle : l'app recrée les séances futures. Une séance avec une exception ou une note est gardée. Elle est retrouvée par (ruleId, originalStart).
T-R4La semaine A/B est calculée à partir de la première semaine A et des semaines sans cours (T6).

7.6 Notes

IDRègle
N-R1Une note stocke le JSON de l'éditeur et une copie en texte brut. Le serveur crée le texte brut.
N-R2Une ligne de tâche stocke seulement le taskId. Elle lit le titre et le statut depuis la tâche.
N-R3Supprimer une ligne de tâche : la tâche reste proposition. L'app affiche « Tâche gardée dans ton planning — Annuler / Supprimer la tâche ».
N-R4Une tâche supprimée ailleurs s'affiche comme « supprimée » dans la note.
N-R5Sauvegarde automatique après 1 à 2 s. Un brouillon local dans le navigateur. Contrôle de version : chaque sauvegarde envoie la version lue. Si elle a changé (autre onglet), l'API refuse (409). L'app affiche « Cette note a changé dans un autre onglet. Recharger ? ». Pas de fusion.

7.7 Suppression et compte

IDRègle
D1Supprimer = deletedAt est renseigné. L'élément n'est plus visible. Pas de purge automatique dans le MVP.
D2Supprimer un cours : ses tâches, notes et séances reçoivent le même deletedAt et le même deletionId. Un script peut les restaurer ensemble.
D3Scripts d'administration (CLI, pas d'écran) : restaurer par deletionId, exporter un espace en JSON, supprimer un compte et ses données.

9. Modèle de données

Objectif : un modèle modulaire. Une nouvelle fonction ajoute un module, des tables ou un consommateur d'événements. Elle ne réécrit pas les tables existantes.

9.1 Principes

IDPrincipe
M1Modules. Une base Postgres. Chaque module a son schéma Postgres, son client Prisma, ses migrations et son package. Un module ne lit jamais les tables d'un autre module : il utilise le service de ce module (injecté). Pas de clé étrangère entre modules : un module garde l'ID, et le code vérifie l'ID avec le service de l'autre module. Les clés étrangères dans un même module sont normales.
M2Colonnes communes sur chaque table de contenu : id (UUIDv7, triable par date), workspaceId, createdAt, updatedAt, createdById, deletedAt, deletionId.
M3L'espace (Workspace) est la frontière des données. Chaque requête filtre par workspaceId et deletedAt IS NULL, avec un seul helper. Le MVP a seulement des espaces personnels. Les groupes seront un nouveau kind d'espace, sans changement sur les tables de contenu.
M4La configuration est une donnée. Types de tâches, règles de révision et réglages du planificateur sont des tables, remplies avec des valeurs par défaut à la création de l'espace. Changer une valeur ne demande pas de déploiement.
M5Liens génériques. Une table Link relie deux entités de modules différents (note → tâche aujourd'hui ; note → note, document → note, carte → note plus tard). Les relations de propriété restent de vraies clés étrangères (bloc → tâche, tâche → cours).
M6Changements entre modules, en mémoire. Après la validation (commit) d'une écriture, le module appelle un notificateur injecté (ChangeNotifier). services/api le relie au planificateur. Pas de table d'événements, pas de worker. Si la replanification échoue, la modification reste ; la prochaine modification ou la prochaine ouverture de l'app replanifie.
M7Temps. Instants en UTC (timestamptz). Règles récurrentes en heure locale + fuseau IANA. Jours sans heure en date.
M8Enum ou table. Enum Postgres pour les états que le code teste (status). Table pour les listes que l'utilisateur ou la configuration peut étendre (types de tâches).
M9JSON seulement pour les charges utiles : contenu d'une note, charge d'un événement, paramètres d'une raison, rapport de risque. Pas de colonne meta générique sur les tables métier.
M10Origine externe. source + externalId sur les séances et les tâches. L'import ICS ou Moodle viendra plus tard sans migration de structure.
M11Noms. Les séances de cours s'appellent ClassSession et ClassSessionRule. Les tables d'authentification s'appellent Auth*. Cela évite le conflit avec la « session » de Better Auth.

10.4 Règles de frontières

IDRègle
A1Un module backend importe seulement les packages lib/* et ses propres fichiers. Il ne peut pas importer un autre module.
A2Un module parle à un autre module par un port (interface qu'il possède). services/api branche le port sur le service de l'autre module (injection de dépendances).
A3Un module utilise seulement son client Prisma. Pas de SQL vers le schéma d'un autre module.
A4Pas de clé étrangère entre modules. Un ID d'un autre module est vérifié par le port avant l'écriture (ex. work demande à academic : « ce cours existe-t-il dans cet espace ? »).
A5Les packages frontend importent le backend seulement avec import type.
A6lib/planner et lib/capture-parser n'ont aucune entrée-sortie : pas de base, pas d'horloge, pas de réseau.
A7Contrôle : règles Biome (retour direct dans l'éditeur et pour les agents) + tests tests/architecture dans la CI (contrôle final).

10.5 Replanification

  1. Un cas d'usage écrit dans sa transaction (ex. work modifie une tâche) et valide.
  2. Après la validation, il appelle ChangeNotifier.notify(workspaceId) (M6).
  3. services/api relie ce notificateur à planning.replan(workspaceId). La replanification tourne dans sa propre transaction, avant la réponse HTTP. La réponse contient donc le nouveau planning.
  4. Si la replanification échoue : la modification reste, l'erreur va dans les journaux. La prochaine modification ou la prochaine ouverture de l'app replanifie.
  5. À l'ouverture de l'app (vue Aujourd'hui ou Semaine) : rattrapage B3 si lastCatchUpAt a plus d'une heure.
  6. Un seul calcul à la fois par espace : verrou Postgres (pg_advisory_xact_lock) sur l'espace.

Conséquence des clients Prisma séparés : une transaction ne couvre qu'un module. Exemple : une ligne de tâche dans une note crée la tâche (module work), puis sauvegarde la note (module notes). Si la note échoue, la tâche reste. C'est accepté (N-R3 garde déjà la tâche).

10.6 API

  • Routes : /api/<module>/…. Chaque module exporte ses routes Hono et leur type.
  • Chaque entrée (corps, paramètres, requête) est validée par un schéma Zod. Les formulaires du frontend utilisent les mêmes schémas.
  • Un middleware lit la session Better Auth et donne userId et workspaceId aux routes. Chaque dépôt filtre par workspaceId et deletedAt IS NULL.
  • Erreurs : toujours { "error": { "code", "message" } }. Un cas d'usage retourne un Result ; la route transforme l'erreur en code HTTP (400, 401, 404, 409).
  • Les données d'un autre utilisateur donnent 404, comme une donnée absente.

10.7 Frontend

  • services/web contient le routeur (React Router), la mise en page et l'assemblage. Chaque package frontend/* exporte ses pages et ses hooks.
  • Toutes les données passent par TanStack Query. Après une modification, les requêtes concernées sont invalidées. Une modification de tâche, d'examen, de séance ou de temps libre invalide aussi le planning.
  • Plusieurs onglets : un onglet recharge ses données quand l'utilisateur y revient (refetchOnWindowFocus). Pas de connexion en direct.
  • Notes : conflit de version = message et rechargement (N-R5).

14. Risques

RisqueRéponse
La saisie manuelle de l'emploi du temps est trop lente. Les testeurs abandonnent le premier jour.Récurrence hebdomadaire. Étape optionnelle. Mesurer la durée de l'onboarding. Si nécessaire, faire l'import ICS plus tôt (M10 le permet).
Le planning n'est pas réaliste.Blocs épinglés, passer et replanifier, temps passé, « besoin de plus de temps », marge avant l'échéance (S14).
Le planning change trop souvent. Les testeurs ne lui font pas confiance.Fenêtre de stabilité, raisons, PlanRun et moveCount pour mesurer les déplacements.
La replanification cache la surcharge.Contrôle de surcharge pour chaque échéance, compteur de replanifications.
Les notes et le planning restent séparés.Lignes de tâche dans les notes, contexte du cours dans les notes. Mesurer les tâches créées depuis une note.
Le papier reste plus rapide pour les notes.Saisie rapide, brouillon local. Mesurer les notes par séance.
Bugs de fuseau horaire et de récurrence.Heure locale pour les règles, UTC pour les instants, tests avec le changement d'heure (FND-6).
Seulement 2 testeurs : les retours ne sont pas objectifs.Utiliser les métriques. Ajouter des camarades quand les testeurs les invitent.
Le planificateur prend trop de temps à construire.Package pur sans dépendance (PLN) : il peut commencer en même temps que les fondations. La vue Aujourd'hui peut d'abord afficher les échéances sans blocs.
Le lien générique Link perd des références.Vérification à l'écriture, test des liens orphelins (OPS-5).
Les fondateurs ne sont pas d'accord, et le travail s'arrête.Chaque fondateur est responsable d'un domaine et y prend les décisions.

15. Décisions et questions ouvertes

Décidé dans cette version

  • Architecture : monolithe modulaire, un service API, un service web (section 10).
  • Pas de worker, pas de notification, pas de mobile.
  • Pas de clé étrangère entre modules ; un client Prisma et des migrations par module.
  • Authentification : Better Auth, email + mot de passe.
  • Pas de PostHog ni de bandeau de consentement : mesures en base de données.
  • Corbeille, export et suppression du compte : à la main, sur demande.
  • Modèles de notes : hors du MVP.
  • Placement des blocs : premier créneau valide, étalé par la limite par tâche et par jour (S12, S13).

Avant de commencer

  • Choisir le domaine de chaque fondateur (propriétaire de chaque épopée).
  • Choisir un nom de produit temporaire.
  • Fixer le temps libre par défaut (A4, S4).
  • Décider si les notes / moyennes entrent dans le MVP (table Grade prête, section 9.3).

Avant l'épopée concernée

  • TSK, EXM, CAP : estimations par défaut (K-R5), règles de révision (E1), cible de saisie 5 ou 10 s, comportement sans date (C5).
  • PLN, RUN : durée des blocs (S3), fenêtre de stabilité (S6), limite de replanification (S11), heure de clôture (S8), message des blocs manqués (B3), limite par tâche et par jour (S13), marge (S14).
  • NOTE : confirmer la syntaxe [], comportement à la suppression d'une ligne (N-R3).
  • FND : hébergement (UE).
