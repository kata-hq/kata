# Database

## How persistence works

- **One Postgres database** (`DATABASE_URL`) for the whole API. Postgres 18 runs in Docker (`compose.yaml`, image `postgres:18.6-alpine`).
- **One Postgres schema per module.** The health module owns schema `health`, the identity module schema `identity`. Future modules: `academic`, `work`, `planning`, `notes`, `platform`.
- **One Prisma schema, client and migrations folder per module**, in `apps/api/src/modules/<module>/prisma/`:
  - `schema.prisma`: `schemas = ["<module>"]` in the datasource and `@@schema("<module>")` on every model.
  - `prisma.config.ts`: points Prisma at the shared `DATABASE_URL` with `?schema=<module>`, so the module's migration history (`_prisma_migrations`) lives in its own schema.
  - `migrations/`: the module's migrations.
  - `generated/`: the generated client (gitignored).
  - `seed.ts`: the module's dev data.
- The module's client factory is in `infrastructure/` (for example `createHealthPrismaClient(databaseUrl)`). It uses `@prisma/adapter-pg` with `schema: "<module>"`. Every module gets the same `DATABASE_URL`; there is no database per module.
- A module reads and writes only its own schema, with its own client.

### Migration order and foreign keys

`apps/api/src/persistence-modules.ts` holds the **ordered module list**. `bun run db:migrate` applies each module's migrations in that order. Today: `health`, `identity`. Target order: `health`, `identity`, `academic`, `work`, `planning`, `notes`, `platform`.

Foreign keys between modules are allowed **only downward**: a table may reference a table of a module that comes **earlier** in the list. Write those foreign keys by hand in the migration SQL (Prisma does not know the other module's models). Foreign keys inside one module are normal Prisma relations.

To add a module: create `modules/<name>/prisma/` like health, then add the module to the list at the right place.

### Repositories, errors and transactions

- Repository interfaces live in `domain/`, Prisma implementations in `infrastructure/`. Repositories return `Result<T, RepositoryError>`.
- `apps/api/src/shared/persistence/prisma-errors.ts` is the only place that maps Prisma errors: `P2002` → `unique-violation`, `P2025` → `not-found`, `P2003` → `foreign-key-violation`. Wrap queries with `runQuery(...)`. Other errors (outage, bug) are thrown.
- `apps/api/src/shared/persistence/unit-of-work.ts`: `createUnitOfWork(client, (tx) => repositories)`. `run(work)` runs the work in one `$transaction`, commits on `Ok`, rolls back on `Err` or on a throw. Example: `createHealthUnitOfWork`. A transaction covers one module only.
- IDs are UUIDv7, generated by Postgres: `@default(dbgenerated("uuidv7()")) @db.Uuid`. Timestamps are `timestamptz`.

### Content tables and the workspace scope

A **content table** holds a workspace's data (courses, tasks, notes, …). The workspace is the data boundary (spec M3). Every content table has the same common columns (spec M2):

```prisma
model Course {
  id          String    @id @default(dbgenerated("uuidv7()")) @db.Uuid
  workspaceId String    @map("workspace_id") @db.Uuid
  createdAt   DateTime  @default(now()) @map("created_at") @db.Timestamptz(6)
  updatedAt   DateTime  @updatedAt @map("updated_at") @db.Timestamptz(6)
  createdById String    @map("created_by_id") @db.Uuid
  deletedAt   DateTime? @map("deleted_at") @db.Timestamptz(6)
  deletionId  String?   @map("deletion_id") @db.Uuid
  // the table's own columns

  @@index([workspaceId])
  @@schema("academic")
}
```

- `id`: UUIDv7, so ids sort by creation time.
- `workspace_id` → `identity.workspace(id)` and `created_by_id` → `identity.user(id)`: cross-module foreign keys, written by hand in the migration SQL (`identity` comes first in the migration order).
- `deleted_at` / `deletion_id`: soft delete. Rows deleted together (a course with its tasks and notes) share one `deletion_id` (spec D1, D2).
- A table without `workspaceId` (the user, the workspace itself, the health checks) is not a content table.

**Every query on a content table filters by `workspaceId` and `deletedAt IS NULL`**, built with one helper from `apps/api/src/shared/persistence/workspace-scope.ts`:

```ts
this.db.course.findMany({ where: scoped(workspaceId, { semesterId }) });
this.db.course.update({ where: scoped(workspaceId, { id }), data });
```

`scoped(workspaceId, where)` adds `{ workspaceId, deletedAt: null }` to the model's filter (the scope wins over a conflicting key); `workspaceScope(workspaceId)` is the bare fragment. The architecture rule `unscopedContentQueries` (`bun run test:arch`) reports any call on a content model (a model with a `workspaceId` field) in a module's `infrastructure/` whose argument does not use `scoped(` or `workspaceScope(`. Creates are exempt (they set `workspaceId` in `data`). Data of another workspace is then "not found", like a missing row (404).

## Commands

Copy `.env.example` to `.env` first. All commands run from the repository root.

| Command | What it does |
|---|---|
| `bun run db:up` | Starts Postgres (`kata-postgres`) and waits for the healthcheck. Port: `POSTGRES_PORT`. First database: `POSTGRES_DB`. |
| `bun run db:migrate` | Creates the `DATABASE_URL` database if missing, then `prisma migrate deploy` for every module, in order. Running it again changes nothing. |
| `bun run db:reset` | Drops the `DATABASE_URL` database, creates it again and migrates. Local hosts only. |
| `bun run db:seed` | Runs each module's seed, in order. Replaces the seeded rows, so it can run again. Local hosts only. |
| `bun run db:studio <module>` | Prisma Studio for one module, e.g. `bun run db:studio health`. Extra flags go to Prisma (`--port 5556`). Without a module it prints the list. |
| `bun run db:generate` | Generates every module's Prisma client. Runs automatically on `bun install` (root `postinstall`), so a fresh clone typechecks and tests. Run it again after you change a `schema.prisma`. |

Fresh start: `bun install && bun run db:up && bun run db:reset && bun run db:seed`.

### New migration

Change the module's `schema.prisma`. With the dev database migrated (`bun run db:migrate`), print the SQL that brings it to the new schema and review it:

```sh
cd apps/api
DATABASE_URL=postgres://kata:kata@localhost:5432/kata bun x prisma migrate diff \
  --config src/modules/<module>/prisma/prisma.config.ts \
  --from-config-datasource --to-schema src/modules/<module>/prisma/schema.prisma --script
```

(Bun loads `.env` from the current folder only, so pass `DATABASE_URL` here.) Save it as `migrations/<yyyymmddhhmmss>_<name>/migration.sql`. Qualify table names with the module schema (`"health"."system_check"`). Then `bun run db:migrate` and `bun run db:generate`.

### Worktrees

All worktrees share the `kata-postgres` container (compose project `kata`) and isolate by database name: give each worktree its own `DATABASE_URL` / `TEST_DATABASE_URL` database name. `db:migrate` creates the database when it is missing. If port 5432 is taken, set `POSTGRES_PORT` and use the same port in the URLs. `bun run dev:isolated` does this for you (database `kata_<worktree>`, own ports): see [workflow.md](workflow.md#worktrees-and-isolated-instances).

## Tests

- Unit tests: `bun run test` (or `bun run test:unit`). It runs each workspace's `test` script (`bun run --filter '*' test`), so each workspace's own `bunfig.toml` applies. `apps/api/bunfig.toml` (and the root `bunfig.toml`) exclude `*.int.test.ts`.
- Integration tests: `bun run test:int`. It uses `bunfig.int.toml`, whose preload (`scripts/ensure-test-db.ts`) creates and migrates `TEST_DATABASE_URL` before any test file loads. The name must end in `_test`.
- In an integration test, get the URL with `testDatabaseUrl()` and empty the tables with `resetTestDatabase(url, ["<schema>"])` (`apps/api/src/shared/persistence/`). Both refuse any database whose name does not end in `_test`. The reset keeps `_prisma_migrations`.

## RGPD register

Every table with personal data must be listed here, in the same PR that creates it.

| Table | Personal data | Purpose | Legal basis | Retention / deletion |
|---|---|---|---|---|
| `identity.user` | `email`, `name`, `image` (unused), `timezone`, `locale` | the account: sign-in, display name, local times | contract | until the account is deleted (D3 admin script), with every row that references it |
| `identity.auth_session` | `token`, `ip_address`, `user_agent`, `expires_at` | keep the person signed in (cookie); IP and user agent are written by Better Auth for session security and rate limiting | contract (session), legitimate interest (security) | deleted at sign-out; expired rows removed by Better Auth; all deleted with the user (cascade) |
| `identity.auth_account` | `password` (scrypt hash), provider tokens (unused for email + password) | check the password at sign-in | contract | deleted with the user (cascade) |
| `identity.auth_verification` | `identifier` (an email), `value` (a token) | short-lived tokens for email verification or password reset (unused until those flows exist) | contract | expires (`expires_at`); removed by Better Auth after use |

Template for a new row: table (`schema.table`), the personal data columns, why we keep them, the legal basis (contract, consent, legitimate interest, legal obligation), and how long we keep them and how they are deleted (for example: deleted with the account).

### Tables without personal data

| Table | Content |
|---|---|
| `health.system_check` | Health check results recorded on demand (dev seed): id, status, time. `GET /api/health` only reads it, so polling does not grow it. |

### Logs

The API writes JSON lines to stdout (`apps/api/src/logger.ts`): `time`, `level`, `msg`, then fields. Logs are not stored by the app; retention is the job of whatever collects stdout.

| Line (`msg`) | Fields |
|---|---|
| `request` (one per request) | `method`, `route` (the matched route pattern such as `/api/health` or `/api/users/:id`, never the real path; `unmatched` when no route matched), `status`, `durationMs`, `requestId` (random UUID, also sent as `x-request-id`) |
| `unhandled error` | `requestId`, `error` (error class name), `stack` |
| `health check failed` (warn) | `error` (error class name, or the `RepositoryError` type), `code` (driver error code such as `ECONNREFUSED`, when there is one). Never the error message. |
| `change listener failed` (warn) | `error` (error class name). No workspace id, never the error message. |
| `auth error` / `auth warning` (error / warn) | `error` (error class name, when Better Auth passes one). Never Better Auth's message: it can quote user input. |
| `invalid environment` | `variables`: name and problem of each bad variable, never its value |
| `api started` / `api stopping` / `api stopped` | `port`, `signal` |

**No personal data in logs.** Never log real request paths (ids and emails can sit in a path), request or response bodies, query strings, headers (cookies, authorization), IP addresses, user agents, user ids, emails or names. Error messages that go into logs must not contain user data either. The `unhandled error` stack starts with the error message, so a driver error that quotes row values would end up there: keep this in mind for the first module with personal data. A new field that could identify a person needs a row in the register above first.
